# دليل البدء السريع

يصحبك هذا الدليل خلال خطوات تثبيت Maestro، وإعداد المشروع، وتنفيذ أول ميزة تحت الإشراف من البداية إلى النهاية.

---

## 1. المتطلبات الأساسية والتثبيت

### المتطلبات الأساسية

تأكد من تثبيت وإعداد ما يلي:
1. أداة **Claude Code** (واجهة سطر الأوامر أو تطبيق سطح المكتب).
2. **تطبيق وكيل Antigravity** مع تسجيل الدخول. (*ملاحظة: تطبيق Antigravity IDE (محرّر الكود) هو تطبيق منفصل ولا يُستخدم هنا.*)
3. بيئة **Python 3.10 أو أحدث** (باستخدام المكتبة القياسية فقط)، وتكون متوفرة كأمر `python` على Windows أو `python3` على macOS وLinux.
4. نظام **macOS**: إذن إمكانية الوصول (Accessibility) للطرفية أو التطبيق المضيف الذي يشغّل Claude Code؛ يسمح هذا الإذن لـ Maestro بإرسال مفتاح الإدخال Return إلى Antigravity، ويطلب macOS هذا الإذن عند التشغيل الأول.
5. أنظمة **Linux**: حزمة `xdg-utils` (وأداة `xdotool` على واجهة X11 إذا كنت ترغب في الضغط التلقائي على مفتاح Enter).

### تثبيت Maestro

انسخ مستودع Maestro وشغّل برنامج التثبيت:

**نظام Windows (عبر PowerShell):**

```powershell
git clone https://github.com/SalehOsman/Maestro C:\Tools\Maestro
python C:\Tools\Maestro\install.py --with-mcp
```

**نظاما macOS و Linux (عبر Bash):**

```bash
git clone https://github.com/SalehOsman/Maestro ~/tools/maestro
python3 ~/tools/maestro/install.py --with-mcp
```

يتحقق برنامج التثبيت من بيئة العمل ويسجّل مهارة Claude Code في المسار `~/.claude/skills/maestro`.

> **تنبيه هام: لماذا يُوصى بالخيار `--with-mcp`؟**  
> يؤدي تشغيل `install.py --with-mcp` إلى تسجيل خادم Maestro MCP في إعدادات Antigravity. يتيح ذلك لـ Antigravity التوقف عند **نقطة مراجعة الخطة** وطرح أسئلة توضيحية أثناء تنفيذ المهمة. ومن دون MCP، يصيغ المنفّذ خطته ثم يبدأ كتابة الكود مباشرة دون مراجعة للخطة عند نقطة التوقف.  
> **بعد تشغيل التثبيت مع المعامل `--with-mcp`، أعد تشغيل تطبيق وكيل Antigravity بالكامل.**

## 2. إعداد المشروع لمرة واحدة

قبل تنفيذ المهام على أي مشروع للمرة الأولى، نفّذ هاتين الخطوتين السريعتين:

### الخطوة 1: تسجيل مساحة العمل في Antigravity

افتح مجلد مشروعك في تطبيق وكيل Antigravity، وأرسل أي رسالة واحدة في صندوق الدردشة (على سبيل المثال: `hello` أو `init`).

لا يسجّل Antigravity مجلد المشروع داخلياً إلا بعد إجراء محادثة فيه. يقرأ Maestro هذا التسجيل حتى يتمكن من تسليم نصوص المهام إلى النافذة المحددة بدقة.

### الخطوة 2: بدء جلستك الأولى في Claude Code

افتح مجلد المشروع نفسه في Claude Code واستدعِ Maestro:

```
/maestro Add a CSV export button to the transactions table
```

لست بحاجة إلى تشغيل أمر `maestro init` يدوياً؛ إذ يستدعي Claude الأمر `init` تلقائياً في الخلفية، ويسألك عن المنهجية التي تود استخدامها، ثم يضبط المشروع وفقاً لذلك:
- **`standard` (موصى بها):** سير العمل القياسي المدمج في Maestro. لا يتطلب أي أدوات خارجية، ويعتمد على مشغلات الاختبارات الحالية في مشروعك.
- **`uem`:** منهجية الهندسة الموحدة بالاعتماد على أدوات Superpowers و EGM و Harness Engineering و AgentShield و ECC (اختياري).
- **`custom`:** للفرق التي تمتلك سير عمل مخصص ومستقر.

عند اختيار المنهجية، اختر `standard` للبدء الفوري دون أي أدوات خارجية، أو `uem` إذا كنت تفضل مراحل هندسية متكاملة وفحصاً أمنياً تلقائياً، أو `custom` للاحتفاظ بقواعد الوكيل المعتمدة في مشروعك. وعند اختيار `uem`، لا تُثبّت الأدوات الخارجية تلقائياً؛ إذ يفحص أمر `maestro tools <project>` المتطلبات، ثم توافق أنت على كل أداة بشكل منفصل قبل أن ينشئ أمر `maestro tools <project> --approve <id...>` وصف مهمة للتثبيت بأوامر مثبتة الإصدار تماماً. وللاطلاع على الدليل الشامل ومصادر الأدوات الرسمية، راجع وثيقة [المنهجيات والأدوات](../en/methodologies.md) (بالإنجليزية).

*(إذا كنت تفضل التحكم اليدوي، يمكنك تشغيل `maestro init <project> [--methodology standard|uem|custom]` مباشرة من سطر الأوامر).*

## 3. ميزتك الأولى من البداية إلى النهاية

هكذا تسير الميزة خلال دورة العمل المتكاملة:

### الخطوة 3.1: العصف الذهني وإنشاء وصف المهمة
يناقش Claude المتطلبات معك موضحاً معايير القبول والحالات الحدية والقيود. وبمجرد اتفاقكما، يكتب Claude وصف المهمة للميزة في الملف `.maestro/tasks/task-001.md`.

### الخطوة 3.2: إرسال المهمة
يرسل Claude وصف المهمة إلى Antigravity باستخدام أمر `maestro send`. يركز Maestro على نافذة تطبيق وكيل Antigravity ويضغط على مفتاح Enter تلقائياً. بعد ذلك، يشغّل Claude أمر `maestro wait` في الخلفية، منتظراً في وضع الخمول دون استهلاك توكن.

### الخطوة 3.3: نقطة مراجعة الخطة (نقطة التوقف 1)
يقرأ الوكيل في Antigravity وصف المهمة، ويفحص المستودع، ويكتب خطة التنفيذ في الملف `.maestro/plans/<feature>.md`.

وعند تفعيل MCP، يتوقف المنفّذ مؤقتاً ويستدعي أداة `maestro_checkpoint`. يستيقظ Claude (برمز الخروج 3)، ويراجع الخطة للتأكد من عدم وجود توسع في النطاق أو اختبارات ناقصة أو تعقيد لا داعي له، ثم يجيب بقرار الاعتماد `APPROVED` (أو يقدم تصحيحات مرقّمة) مع تحديد عمق المراجعة (سريعة مقابل شاملة).

### الخطوة 3.4: التنفيذ الموجّه بالاختبارات
ينفّذ Antigravity الخطة المعتمدة بالبدء بالاختبارات أولاً عبر دورة «الفشل ← النجاح ← التحسين»:
1. كتابة اختبارات فاشلة وتوثيق مخرجات الفشل (الأحمر).
2. كتابة الحد الأدنى من الكود البرمجي لاجتياز الاختبارات.
3. تشغيل حزمة الاختبارات وأوامر التحقق الذاتي وتوثيق أدلة النجاح (الأخضر).
4. كتابة تقرير الإنجاز النهائي في الملف `.maestro/reports/task-001.done.md` كآخر خطوة.

### الخطوة 3.5: المراجعة والتحقق (نقطة التوقف 2)
بمجرد ظهور ملف التقرير، يستيقظ Claude تلقائياً:
- لا يعتمد Claude على التقرير كدليل، بل يعيد تشغيل الاختبارات بنفسه وبشكل مستقل.
- يفحص Claude فروقات الكود عبر `git diff` للتأكد من عدم وجود تعديلات خارج النطاق أو تغييرات عرضية.
- يشغّل Claude أداة `maestro testdiff` لضمان عدم حذف أي اختبارات سابقة أو تضعيفها أو تخطيها.
- في المراجعات الشاملة، يشغّل Claude اختبارات الطفرات واختبارات القبول المحجوبة المخزنة خارج المستودع.
- ينشئ Claude سجلاً للمراجعة في الملف `.maestro/reviews/<feature>-round-1.md`. وإذا تطلب الأمر إصلاحات، يرسل Claude وصف مهمة إصلاحية (وذلك ضمن جولتي مراجعة كحد أقصى).

### الخطوة 3.6: الموافقة على الدمج
بعد اجتياز جميع معايير القبول وبوابات الجودة، يسجّل Claude قبول الميزة في `feature_list.json` ويعرض العمل المكتمل والأدلة وخطوات التحقق اليدوي. تراجع العمل بنفسك وتعطي الموافقة النهائية لدمج الفرع.

## 4. ما يضيفه Maestro إلى المشروع

يحافظ Maestro على تنظيم نظيف وواضح لمساحة العمل، ولا يُجري أي تعديل على ملفات `AGENTS.md` أو `GEMINI.md` الموجودة في مشروعك:

```
<project>/
  feature_list.json              سجل الميزات: الحالة، الأدلة، وقرار المراجعة
  progress.md                    سجل التطور المعماري وتعديلات الاختبارات وملاحظات الطفرات
  session-handoff.md             ملخص العمل المنجز ونتائج التحقق والخطوات التالية
<project>/.maestro/
  config.json                    إعدادات المشروع: أوامر الاختبارات، ومسارات الخطورة، وجولات المراجعة
  ROLES.md                       العقد المحدد للأدوار والمسؤوليات
  EXECUTOR_RULES.md              التعليمات التي يتبعها منفّذ Antigravity
  report-template.md             القالب القياسي لكتابة تقارير الإنجاز
  tasks/task-NNN.md              أوصاف المهام المنشأة بواسطة Claude
  plans/<feature>.md             خطط التنفيذ التي يكتبها وكيل Antigravity
  reports/task-NNN.done.md       تقارير الإنجاز النهائية المتضمنة أدلة التطوير بالاختبارات
  reviews/<feature>-round-N.md   جولات المراجعة مع الملاحظات والنتائج (جولتان كحد أقصى)
  questions/task-NNN-qN.*        الأسئلة والأجوبة أثناء تنفيذ المهمة (المتبادلة عبر MCP)
  progress/task-NNN.log          سجل تتبع التقدم للمهام طويلة التنفيذ
  active.json                    علامة مؤقتة تتواجد فقط أثناء تشغيل مهمة نشطة
```

تجدر الإشارة إلى أن مهارة Claude Code وقواعد المنفّذ (`EXECUTOR_RULES.md`) والقوالب مكتوبة عمداً باللغة الإنجليزية؛ وذلك لأن الوكلاء البرمجيين ونماذج الذكاء الاصطناعي هي التي تقرؤها وتتعامل معها، مما يضمن دقة التوجيهات ومنع أي التباس في التوجيهات أثناء التنفيذ الآلي.

> **فائدة:** يمكنك ضم مجلد `.maestro/` إلى نظام تتبع النسخ `git` للاحتفاظ بتاريخ أوصاف المهام والخطط والمراجعات. واحرص دائماً على إضافة `.maestro/active.json` إلى ملف `.gitignore`؛ لكونه ملف قفل مؤقت.

## 5. المنهجيات بالتفصيل

تحدد المنهجية **كيفية عمل المنفّذ** ومراحل بنائه للكود، دون المساس بتوزيع الأدوار الثابت بين المستخدم و Antigravity و Claude Code؛ إذ لا يعتمد المراجع على تقرير المنفّذ أو ادعاءاته، بل يعيد التحقق المستقل من الاختبارات والفروقات دائماً.

### منهجية `standard` (القياسية المدمجة)
- **طبيعتها:** المنهجية الافتراضية في Maestro؛ لا تتطلب أي أدوات خارجية، وتعتمد كلياً على مشغلات الاختبار وأدوات التدقيق الموجودة في مشروعك.
- **مراحل المنفّذ:**
  1. **الخطة:** صياغة خطة التنفيذ مع بديل مستبعد وسبب استبعاده وقائمة الاختبارات المحددة.
  2. **نقطة مراجعة الخطة (نقطة التوقف 1):** التوقف واستدعاء نقطة الفحص عبر خادم MCP وانتظار اعتماد Claude الصريح.
  3. **فرع العمل:** العمل داخل فرع مستقل `feature/<id>` دون دمج أو دفع مباشر.
  4. **التطوير بالاختبار أولاً (TDD):** كتابة الاختبار الفاشل وتوثيق الفشل (الأحمر) ← كتابة الحد الأدنى من الكود لاجتياز الاختبار وتوثيق النجاح (الأخضر) ← تحسين الكود مع استمرار اجتياز الاختبارات. ولا يجوز حذف أو إضعاف أي اختبار دون توثيق السبب الصريح في `progress.md`.
  5. **التحقق الذاتي:** تشغيل أوامر التحقق الكاملة وفحص الطفرات إن وُجد، وتحديث `feature_list.json` بحالة `status: "passing"` مرفقة بالأدلة.
  6. **التقرير النهائي (نقطة التوقف 2):** كتابة تقرير الإنجاز في الملف `.maestro/reports/task-NNN.done.md` كآخر خطوة.
- **ما يفحصه المراجع:** إعادة تشغيل الاختبارات وأوامر التحقق بشكل مستقل، ومراجعة نطاق التغييرات في `git diff`، وتشغيل `maestro testdiff` لرصد أي اختبارات محذوفة، والتحقق من تغطية المتطلبات ومسارات الأخطاء، وإجراء اختبارات الطفرات والاختبارات المحجوبة للمناطق الحساسة.

### منهجية `uem` (منهجية الهندسة الموحدة)
- **طبيعتها:** منهجية متقدمة تدمج قدرات وكلاء متعددة: Superpowers و EGM و Harness Engineering و AgentShield، بالإضافة إلى ECC (اختياري).
- **ثوابت بيئة العمل (ثوابت Harness):** المستودع هو مصدر الحقيقة المعتمد (`feature_list.json` و `progress.md` و `session-handoff.md`)، وميزة واحدة نشطة في كل مرة، ولا انتقال لحالة النجاح دون تشغيل أمر التحقق الفعلي وتوثيق مخرجاته.
- **المراحل الأربع:**
  1. **التأسيس:** العصف الذهني عبر Superpowers، والنقد المعماري المعاكس عبر أدوار EGM، وإدراج الميزة في `feature_list.json`.
  2. **الخطة:** خطة تنفيذ دقيقة، ومراجعة الجاهزية، واستدعاء نقطة الفحص والانتظار حتى الاعتماد (نقطة التوقف 1).
  3. **البناء:** عزل مساحة العمل عبر تفريعات `git` والتنفيذ بأسلوب TDD الصارم والتحقق المستمر.
  4. **التحقق والتسليم:** التحقق الشامل ومراجعة الكود، وتشغيل الفحص الأمني التلقائي عبر النسخة المثبتة محلياً حصراً: `npx --no-install ecc-agentshield scan --path .`، وتحديث ملفات الحالة، وكتابة التقرير النهائي (نقطة التوقف 2).
- **التوافق مع أدوار Maestro:** يقتصر دور المنفّذ على تسجيل `status: "passing"`، بينما قرار الاعتماد النهائي `review: accepted` هو صلاحية حصرية للمراجع Claude Code؛ كما يُمنع تماماً تشغيل أدوات غير مثبتة من الشبكة عبر `npx --yes`.

### منهجية `custom` (المنهجية المخصصة)
- **طبيعتها:** مصممة للفرق والمشاريع التي تمتلك تعليمات وسير عمل خاصاً في ملفات `AGENTS.md` أو `GEMINI.md`.
- **عقد Maestro الأدنى (8 نقاط ملزمة):**
  1. **الالتزام بالنطاق:** تنفيذ المهمة المحددة والملفات المذكورة فقط.
  2. **نقطة مراجعة الخطة:** إرسال الخطة والتوقف عبر خادم MCP حتى صدور الاعتماد.
  3. **أمان `Git`:** عدم الدمج أو إعادة البناء أو التفرع غير المصرح به.
  4. **الأدلة الملموسة:** تشغيل كل أمر قبول وتوثيق مخرجات الطرفية الفعلية.
  5. **حماية الاختبارات:** منع حذف أو تضعيف أو تخطي أي اختبار دون تبرير مكتوب.
  6. **حدود صلاحية المراجعة:** الامتناع عن تسجيل قرار الاعتماد؛ إذ يعود القرار للمراجع حصراً.
  7. **التقرير كآخر خطوة:** كتابة التقرير النهائي وفق القالب المعتمد في نهاية العمل.
  8. **الأمان والحماية:** عدم لمس الأسرار أو المفاتيح البرمجية، وعدم تشغيل برمجيات غير مثبتة الإصدار من الشبكة.
- **التطبيق الصارم:** تبقى المراجعة الشاملة والمستقلة من Claude Code مطبقة بكامل معاييرها وفحوصاتها.

## 6. استكشاف الأخطاء وإصلاحها

| العَرَض | السبب | الحل |
|---|---|---|
| يبلّغ أمر `init` بأن Antigravity لا يتعرف على المجلد | لم يقم Antigravity بفهرسة مساحة العمل بعد | افتح المجلد في تطبيق وكيل Antigravity وأرسل رسالة واحدة. ثم أعد تشغيل `init` أو `/maestro`. |
| ينتهي أمر `send` برمز الخروج 2 | تعذر التركيز على نافذة Antigravity أو تم منع الضغط التلقائي على مفتاح Enter | تحقق من مخرجات الطرفية. في Windows، تأكد من أن نافذة Antigravity ليست مصغرة. وفي macOS، امنح إذن الوصول للطرفية. وفي Linux Wayland أو عند غياب أداة `xdotool`، اضغط على مفتاح Enter في Antigravity يدوياً؛ وسيواصل Claude الانتظار. |
| يصل نص المهمة إلى مشروع Antigravity خاطئ (أو يرفض أمر `send` الإرسال) | تعذر مطابقة معرّف المشروع مع المجلد المطلوب | يرفض أمر `send` الإرسال افتراضياً لتجنب توجيه المهمة إلى مشروع غير مقصود. افتح المجلد في تطبيق وكيل Antigravity وأرسل رسالة واحدة لتسجيله، ثم أعد تشغيل `maestro init` حتى يطبع معرّف المشروع. استخدم `--allow-current-project` فقط إذا كنت تقصد صراحةً الإرسال إلى المشروع المختار حالياً. |
